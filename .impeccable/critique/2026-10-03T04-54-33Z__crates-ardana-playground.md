## Design Specificity Verdict
**LLM assessment:** Authored for Ardana, and the new states stay in its world. The download bar is the answers' own 6px track with a gray fill, never ink, because nothing is answered yet; the CLI handoff is the landing's command row with the gray `$` prompt and the copy key; where an answer came from is one clause in the last-run line ("in this tab on WebGPU") and in the raw panel's caption ("Sent · in this tab"). The layout is the category's, as the brand commitment requires. The flaw is the system's quiet sameness flattening the stakes: the 467.7 MB download line has the weight of "Add a question to run" (gray, 14px, 500), and the public demo's best moment, a decision model answering inside the visitor's own tab, is a 13px gray clause.

## Overall Impression
The new states look as if they were always part of Ardana: the detector finds nothing to object to and A finds the vocabulary intact. What breaks is the behaviour around the first expensive action the page has had. A first run in the tab downloads 467.7 MB; on a phone nothing in view says so, nothing can stop it, and a screen reader hears nothing until it is over. The peak is real: the answers arrive as one ink bar each with exact mono figures and "in this tab on WebGPU", and a second visit answers in about 1.2 s with no download. The end is strong: PUBLIC ends on the install line and `ardana run` with the exact request. The valleys sit between. The download has honest bytes and a bar, but no size before committing on a phone, no "kept for next time" while it runs, no stop, and a stage line that says Pulling and Starting when neither is happening. The held "has not pulled decider-4b" has a plain reason and one action, but it ends in a terminal, and a press on the held Run shows nothing. The failure is emscripten text with no exit. Cognitive load is moderate, failing 2 of 8: minimal choices (an 8-row Model select in which three names appear twice with different sizes, told apart only by group labels seen while the list is open) and working memory (on phones, where Run answers and what it costs is said only in the drawer). The single biggest opportunity: make the first in-tab run's cost explicit and revocable where Run is, at every width, and make "in this tab" the public demo's display moment instead of a 13px clause.

## What's Working
1. **The new states speak the existing vocabulary.** The download bar is the answers' own track, gray because nothing is answered yet; the CLI step reuses the landing's command row and `$` prompt; a tab answer reads byte for byte like a server's. B's scans and overlay runs find nothing off-system in any of them; the only rendered finding is DESIGN.md's own caret.
2. **The held state is coherent for assistive technology.** The reason is Run's accessible description ("This server has not pulled decider-4b: run it with the ardana CLI Show the command", `a11y.json`); the select's description carries the model note; Run is `aria-disabled` and keeps focus; "Show the command →" moves focus to Snippets; the skip link lands before the state editor.
3. **Round 2's layout bugs are closed.** Run keeps one width (106px at rest and while loading); the answer bars restack in a narrow column (tracks 351, 392 and 435px at 1024, 1100 and 1180; `recheck.json`).

## Priority Issues
1. **[P1] The 467.7 MB first run is one unguarded, unstoppable tap on phones.** States `public` and `browser-download` at 390 and 320 (and at any width with the sidebar collapsed), light and dark. The only disclosure is `#model-note` (`ui/sidebar.rs:185–209`) in the closed drawer; before Run the main column mentions only the CLI's 811.8 MB (`mainMentionsSize: {has467: false, has811: true}`, `tab-mobile-light-normal.json`). Share links open PUBLIC straight onto the In browser row with Run live (`shots/public-share-mobile-light.png`), and `linked_row` (`deck.rs:58–63`) does the same on LOCAL for unpulled browser models. Nothing stops it: `engine.rs`, `engine.js` and `deck.rs` have no abort path; picking decider-2b at 242.8 MB let 224.9 MB more arrive, and decider-0.8b's answers landed marked "From last run · inputs changed" (`shots/tab-switched-mobile-dark-switch.png`). Read from the code, not exercised: `?autorun=1` (`ui/mod.rs:160–174`) calls `deck.run()` once the model list loads without asking where the pick runs, so an autorun link onto an In browser row would start the download with no tap at all.
   - **Why it matters:** a cellular-data cost the visitor never agreed to, at the public demo's front door; it breaks PRODUCT.md's "Local and honest".
   - **Fix:** while an In browser row is picked and its files are not cached (`caches.match`), the quiet banner says at every width "Run downloads decider-0.8b into this tab once: 467.7 MB, kept by this browser."; a Stop action beside it, styled like "Show the command", backed by an `AbortController` on `browser_file`; picking another row aborts too; autorun never starts an uncached download; optionally a confirmation under `saveData`.
   - **Suggested command:** $impeccable harden, then $impeccable clarify
2. **[P1] In-tab progress is silent to screen readers (WCAG 2.2 SC 4.1.3 Status Messages).** State `browser-download`, every viewport. `#run-note` (`ui/topbar.rs:122–164`) is a plain paragraph, not a live region, and the page's status region (`ui/mod.rs:196`) reads only finished runs (`run_status`), so only the final "Answered by…" is announced. Run's description (`aria-describedby="run-note"`, `topbar.rs:93`) reads "Downloading decider-0.8b into this tab: 118.8 MB of 467.7 MB 1.18770e+8"; the progress bar's name is "Download" and its value raw bytes (`a11y.json`).
   - **Why it matters:** a user who presses Ctrl+Enter from the editor hears nothing for 20 seconds to several minutes, then an answer (checked in Chrome's accessibility tree, not with VoiceOver or NVDA).
   - **Fix:** announce stage changes, and every 10% of a download, through the existing status region or a polite `role="status"` span; give `<progress>` an `aria-valuetext` ("118.8 MB of 467.7 MB") or hide it from the tree; point Run's description at the sentence alone.
   - **Suggested command:** $impeccable audit, then $impeccable harden
3. **[P2] The stage line misreports what the tab is doing.** State `browser-download`. First run (`tab-mobile-light-normal.json`): 57 ms Pulling, 61 ms Starting, 189 ms Downloading 2.3 MB, 962 ms Starting (the bar vanishes at 0.5%), 1332 ms Downloading, 1345 ms Starting, 1351 ms to 21.3 s Downloading, 21.3 s Starting (1.6 s), 22.9 s Running. Every in-tab run, cached or not, opens on "Pulling the browser files of decider-0.8b (467.7 MB) on the server" for 4–300 ms, because `deck.rs:508` and `engine.rs:117` set Pulling before the server is asked, and `engine.rs:350` drops back to Starting after each of the three files. The banner is not sticky (`styles/shell.css:279`): scrolled to Snippets, only "Loading▮" remains.
   - **Why it matters:** the one line that explains a long wait says things that are not happening, then leaves when the visitor scrolls.
   - **Fix:** say Pulling only if the profile request is still pending after about 400 ms; one Downloading stage across all three files; Starting only before the session is created; the banner sticky while a run is in flight.
   - **Suggested command:** $impeccable clarify, then $impeccable polish
4. **[P2] The `run-command` state gives everyone the newcomer's path.** LOCAL and PUBLIC (`shots/run-command-shown-desktop-light.png`, `shots/public-4b-narrow-light.png`). On LOCAL, "Install ardana" is shown to someone already running `ardana serve`; `ardana run` answers in the terminal; `ardana pull decider-4b` is never offered; `/v1/models` is refetched only after a run (`ui/mod.rs:176–185`), so after a pull the page still says "has not pulled" until reloaded. On PUBLIC, "This server has not pulled decider-4b" implies the server is missing something, and no in-tab alternative is offered.
   - **Why it matters:** the handoff is right but addressed to the wrong person: the operator gets an install line, the visitor gets blame on a server that never runs models, and neither gets the shortest path.
   - **Fix:** on LOCAL offer `ardana pull decider-4b` first, drop the install line, and refetch the list on `visibilitychange` and focus; on PUBLIC say "decider-4b runs with the ardana CLI on your machine" and add "Run decider-0.8b in this tab instead".
   - **Suggested command:** $impeccable clarify and $impeccable onboard
5. **[P2] An in-tab failure is cryptic and does not clear.** The `browser-results` failure, desktop dark (`shots/tab-retried-desktop-dark-fault.png`): "No response · the request was not answered." (`ui/questions.rs:176`) over raw text ending "Aborted(both async and sync fetching of the wasm failed). Build with -sASSERTIONS for more info"; the last-run line says "No response · 0 ms". With the network back, Run failed again in about 0.3 s; only a reload recovered (1.4 s, all three files still kept; `reload-after-fault.json`). Cause: `engine.js` memoises the rejected import (`modules[device] ??= import(...)`).
   - **Why it matters:** the visitor gets nothing to act on, and the obvious retry cannot work.
   - **Fix:** title it as the tab's failure with one cause and one next step; keep the raw text in a disclosure; drop the rejected entry and re-import with a cache-busting query; say "Reload the page" when a retry cannot work.
   - **Suggested command:** $impeccable harden and $impeccable clarify
